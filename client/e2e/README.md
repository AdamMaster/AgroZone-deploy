# E2E-тесты (Playwright)

Автоматические тесты для двух реально работающих на сайте способов входа/регистрации
(телефон + звонок для подтверждения, и Яндекс OAuth), плюс смены пароля и почты в
настройках профиля. Ничего из этого не трогает ваш обычный (боевой/dev) сайт —
тесты поднимают отдельный клиент, отдельный сервер и отдельную базу данных.

**Перед тем как читать дальше:** этот набор тестов был написан и внимательно
вычитан по исходному коду, но ни разу не запускался целиком в том окружении, где
писался (там не было сети до `localhost` и до серверов, откуда Playwright
скачивает браузеры). Считайте первый реальный запуск на вашей машине приёмкой —
см. раздел «Если что-то пойдёт не так» в конце файла.

---

## 0. Про cookie сессии в тестах (уже исправлено, просто для понимания)

При подготовке этих тестов обнаружилась нестыковка: `server/.env.test` называет
cookie сессии `e2e_session` (переменная `SESSION_NAME`) — специально, чтобы
тестовая сессия никогда не перепуталась с обычной dev-сессией в том же браузере
на `localhost` — а `client/src/middleware.ts` (защита страниц `/profile/*`)
проверял cookie по жёстко зашитому имени `'session'`, игнорируя `SESSION_NAME`.

Это уже исправлено: `middleware.ts` теперь читает имя cookie из
`process.env.SESSION_NAME` (с запасным вариантом `'session'`, если переменная не
задана — обычная разработка не меняется), значение прокинуто через `next.config.ts`
(`env.SESSION_NAME`), а `test:e2e:client` в `client/package.json` передаёт
`SESSION_NAME=e2e_session` явно. Отдельно ничего делать не нужно — упоминаю
здесь на случай, если при отладке увидите переход между `session`/`e2e_session`
в разных местах и не будете понимать, откуда это.

## 1. Разовая подготовка (один раз на машине)

1. **Создайте тестовую базу данных** в том же Postgres, что использует обычный
   сервер (порт 5433 — см. `server/.env.test`), но отдельную, с именем
   `greenbase_test`. Например, через `psql`:
   ```
   psql -h localhost -p 5433 -U root -c "CREATE DATABASE greenbase_test;"
   ```
   (или тем же способом, каким обычно создаёте базы — через любую GUI-программу
   для Postgres, вроде DBeaver/pgAdmin).

2. **Примените миграции к этой новой базе** (из папки `server/`):
   ```
   npm run test:e2e:db:deploy
   ```

3. **Установите зависимости и браузер для Playwright** (из папки `client/`).
   `npm install` уже был выполнен ранее для этого проекта — не нужно повторять,
   если `client/node_modules` уже на месте. А вот браузер Playwright скачивает
   отдельно и его точно нужно поставить один раз:
   ```
   npx playwright install chromium
   ```

## 2. Перед каждым запуском тестов

Тестам нужны четыре вещи, поднятые заранее: Postgres, Redis, Mailpit и мок-сервер
Zvonok. Сам Playwright (`npx playwright test`) поднимет только клиент и сервер
(через `webServer` в `playwright.config.ts`) — остальное нужно запустить руками.

1. **Postgres и Redis** — если вы обычно разрабатываете локально, они, скорее
   всего, уже подняты (тот же `docker-compose.yml`, что и всегда). Если нет —
   поднимите как обычно.

2. **Mailpit** (подменяет реальную отправку почты Gmail — письма о смене почты
   будут падать сюда, а не на реальный ящик). Из корня проекта:
   ```
   docker compose -f docker-compose.yml -f docker-compose.test.yml up -d
   ```
   Веб-интерфейс Mailpit (можно посмотреть письма глазами) — http://localhost:8025

3. **Мок-сервер Zvonok** (подменяет платный сервис звонков — тесты регистрации
   по телефону не должны никому реально звонить). В отдельном терминале, из
   папки `server/`:
   ```
   npm run test:e2e:mock-zvonok
   ```
   Оставьте это окно открытым, пока гоняете тесты.

4. **Сами тесты** — из папки `client/`:
   ```
   npx playwright test
   ```
   Это само поднимет клиент на порту 3001 (поверх тестового сервера на 4001) и
   сервер на порту 4001 (поверх `greenbase_test`), дождётся их готовности,
   один раз создаст двух фикстурных тестовых пользователей (см.
   `e2e/global-setup.ts` и `e2e/fixtures/test-users.ts`) и запустит все специки.

   Полезные варианты запуска:
   - `npx playwright test --ui` — интерактивный режим с визуальным
     воспроизведением шагов (`test:e2e:ui` в `package.json`).
   - `npx playwright test e2e/login.spec.ts` — только один файл.
   - `npx playwright show-report` — открыть HTML-отчёт после прогона в CI-режиме.

## 3. Если нужно начать с чистого листа

Специки написаны так, чтобы их можно было гонять повторно без сброса базы
(каждый либо только читает, либо сам возвращает состояние обратно, либо
использует заведомо новые случайные значения — см. комментарии в начале
каждого файла в `e2e/`). Но если что-то пошло не так на середине прогона и
данные могли остаться в промежуточном состоянии, проще всего пересоздать схему
целиком (из `server/`):

```
dotenv -e .env.test -- npx prisma migrate reset --force
```

Это удалит все данные из `greenbase_test` и заново накатит миграции. После
этого `global-setup.ts` при следующем запуске тестов заново создаст
фикстурных пользователей.

## 4. Что тестируется и где

| Файл | Что проверяет |
|---|---|
| `login.spec.ts` | Вход по телефону+паролю: успех, неверный пароль, несуществующий пользователь — с реальными текстами ошибок из `AuthService.login`. |
| `password-change.spec.ts` | Смена пароля в `/profile/settings/security`: успех + регрессия (выход и повторный вход НОВЫМ паролем), и отдельно — неверный текущий пароль (+ проверка, что пароль реально не изменился). |
| `email-change.spec.ts` | Запрос смены/привязки почты → письмо в Mailpit → переход по ссылке из письма → подтверждение → вход НОВОЙ почтой. |
| `phone-registration.spec.ts` | Полная регистрация по телефону: ввод номера → экран ожидания звонка → мок Zvonok подтверждает его через ~1.5с → имя/пароль → пользователь авторизован. |
| `oauth-yandex.spec.ts` | Смоук: кнопка «Яндекс» ведёт на настоящий `oauth.yandex.ru` с верными параметрами (`client_id`, `redirect_uri`, `response_type=code`, `state`). Реальный вход через Яндекс НЕ выполняется и не должен — вводить туда настоящие учётные данные в автотесте нельзя. |

Email/Google-регистрация не тестируются — по условию задачи они мертвы (недоступны
из интерфейса сайта).

## 5. Технические решения, о которых стоит знать

- **Капча подменяется стабом** (`e2e/fixtures/captcha-stub.ts`). На сервере проверка
  капчи полностью отключена в dev-режиме (`CaptchaGuard.canActivate` →
  `isDev(configService) => true`, а `NODE_ENV='development'` и в `.env`, и в
  `.env.test`) — то есть даже настоящий токен от Яндекса сервер бы не проверял.
  А сам виджет Yandex Smart Captcha требует, чтобы домен `localhost:3001` был явно
  разрешён в кабинете Яндекса для используемого sitekey — полагаться на это в
  автотестах ненадёжно. Поэтому вместо настоящего `captcha.js` тесты подсовывают
  минимальную реализацию того же публичного API, которая сразу же "решает" капчу.
  Если Яндекс когда-нибудь изменит формат этого API — стаб придётся обновить
  (см. `node_modules/@yandex/smart-captcha/index.js` как источник истины).
- **Один воркер** (`workers: 1` в `playwright.config.ts`) — большинство специков
  логинятся под общими фикстурными пользователями и меняют их состояние в БД;
  параллельный запуск означал бы гонки за одну и ту же строку.

## 6. Если что-то пойдёт не так при первом запуске

Это первый реальный прогон этих тестов — они писались и вычитывались по
исходному коду проекта, но не выполнялись живьём (окружение, где они создавались,
не имело сети ни до `localhost`, ни до серверов, откуда Playwright скачивает
браузеры). Наиболее вероятные места, за которыми стоит присмотреть особо
внимательно при первом запуске:

- **Mailpit REST API** (`e2e/fixtures/mailpit.ts`) — форма ответа
  `GET /api/v1/messages` и `GET /api/v1/message/:id` соответствует официальному
  API Mailpit v1 на момент написания, но не проверялась живым запросом. Если
  `email-change.spec.ts` падает с ошибкой вида «письмо не найдено» — сначала
  откройте http://localhost:8025 глазами и убедитесь, что письмо вообще пришло;
  если пришло, но тест его не находит — сверьте реальную форму JSON-ответа с
  тем, что ожидает `fetchLatestConfirmationPath` в `mailpit.ts`, и поправьте
  разбор.
- **Роль `menuitem` у пунктов меню профиля** — выход из аккаунта в
  `password-change.spec.ts`/`email-change.spec.ts` ищет
  `page.getByRole('menuitem', { name: 'Выйти' })`. Компонент собран на
  `@base-ui/react/menu`, которая по умолчанию должна проставлять ARIA-роль
  `menuitem`, но это не проверялось в реальном браузере — если локатор не
  находит элемент, посмотрите через Playwright Inspector (`--debug`) или
  `--ui`, какая роль/имя реально доступны у пункта «Выйти».
- **`redirect_uri` в `oauth-yandex.spec.ts`** — `server/.env.test` содержит
  `APPLICATION_URL='http://localhost:4000'` (порт обычного dev-сервера, а не
  4001, на котором в тестах реально поднимается сервер). Тест сознательно не
  проверяет конкретный порт в `redirect_uri`, только сам путь
  (`/auth/oauth/callback/yandex`), так что это не должно ломать тест — но если
  вы захотите когда-нибудь довести E2E-колбэк OAuth до конца (не только смоук),
  эту переменную стоит поправить на `http://localhost:4001`.
- **Общий тайминг** — таймауты подобраны с запасом (например, до 15с на шаг
  подтверждения телефона при том, что мок отвечает за 1.5с, а фронт опрашивает
  раз в 4с), но на медленной машине или при холодном старте `next dev`
  первый прогон может быть заметно медленнее последующих.

Если один из специков падает — это не повод считать всю работу бракованной:
дайте знать, что именно упало (сообщение об ошибке + какой файл), это почти
всегда точечная правка селектора или таймаута, а не проблема архитектуры тестов.
