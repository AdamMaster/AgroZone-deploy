# Аудит скорости клиента AgroZone

Дата: 19.09.2026. Изменений в код не вносилось — только анализ. Ниже — находки по приоритету.

## Оговорка про билд

Попытался собрать прод-билд (`npm run build`) прямо в текущем окружении, чтобы получить точные цифры First Load JS по каждому роуту — не получилось: `node_modules` установлен под Windows, а в моём окружении Linux, из-за чего падают нативные бинарники (`lightningcss`) и не резолвится шрифт (сетевые ограничения именно этой сессии). Это не баг проекта, а ограничение окружения аудита. Если нужны точные цифры по бандлам — прогони `npm run build` у себя и пришли хвост вывода (там таблица Route / Size / First Load JS), либо попроси меня это сделать в следующий раз через актуальный dev-канал.

Все находки ниже — из статического анализа кода, конфигов и реальных файлов.

## Критично

### 1. Все 14 иконок категорий на главной помечены `priority` — конкурируют за LCP

Файл: `client/src/components/features/categories/components/category-item.tsx`

`priority` в `next/image` — это не просто "загрузи eager", это ещё и `<link rel="preload">` в `<head>`, зарезервированный для 1-2 самых важных изображений на странице (обычно то самое, что и есть LCP-элемент). Тут `priority` стоит сразу у **всех 14** карточек категорий на верхнем уровне — то есть браузер получает 14 одновременных preload-запросов "высшего приоритета", которые конкурируют за пропускную способность с реальным LCP-элементом страницы (и вообще с шрифтами/CSS/JS). Чем больше "priority"-изображений, тем меньше по факту толку от приоритета — это классический анти-паттерн.

В коде это осознанный костыль поверх другой проблемы (см. комментарий в файле): раньше эти же иконки грузились с дефолтным `loading="lazy"`, и на проде (не на деве) не догружались вообще — оставались пустыми. Вместо того чтобы разобраться, почему `lazy` не работал именно на проде (подозреваю на позиционирование `absolute` + `overflow-hidden` у родителя — IntersectionObserver может не видеть такие элементы корректно, либо разница в hydration timing), проблему заглушили тем, что убрали lazy loading вообще, для всех сразу.

**Что стоит сделать (не делал, просто вариант):** разобраться в первопричине бага с lazy-loading (скорее всего, дело в позиционировании/оверфлоу родительского контейнера), вернуть `priority` только первым 3-4 карточкам (то, что реально видно во viewport при первой отрисовке на мобильном/десктопе), остальным — обычный lazy.

### 2. Нигде в клиенте не используется `next/dynamic` — ни разу

Проверил весь `client/src` — `next/dynamic` не импортируется НИ В ОДНОМ файле. Это значит, что вообще все тяжёлые библиотеки, которые нужны не на каждой странице (а иногда — не при каждом взаимодействии с уже открытой страницей), попадают в бандл сразу, без отложенной загрузки:

- `yet-another-react-lightbox` (+ его CSS) — статически импортируется прямо в `ad-detail.tsx` (страница объявления — одна из самых посещаемых на сайте), хотя лайтбокс открывается только по клику на фото. Плюс тот же паттерн в админской `ad-moderation-detail.tsx`.
- `recharts` — статически импортируется в `ad-views-stats.tsx`, который рендерится внутри `ad-detail.tsx` и `ad-stats.tsx`. Recharts — довольно тяжёлая библиотека (тянет d3-примитивы), а график статистики просмотров нужен явно не всем посетителям страницы объявления (в лучшем случае — только владельцу).
- `react-dadata` (+ CSS) — подсказки адреса, нужны только в формах (подача объявления, возможно чекаут/адрес).
- `@yandex/smart-captcha` — капча, нужна только в формах авторизации/регистрации.
- `socket.io-client` — см. следующий пункт.

Всё это — кандидаты на `next/dynamic(() => import(...), { ssr: false })`, особенно там, где виджет открывается по явному действию пользователя (лайтбокс, капча) — тогда его JS вообще не должен грузиться, пока пользователь не кликнул.

### 3. `SupportChatWidget` (и вместе с ним `socket.io-client`) смонтирован глобально в корневом layout

Файл: `client/src/app/layout.tsx` → `<SupportChatWidget />` внутри `<MainProvider>`, рендерится на КАЖДОЙ странице сайта без исключений.

В коде это осознанное решение (см. комментарий в `support-chat-widget.tsx`) — сокет открывается сразу, чтобы бейдж "непрочитано" на кнопке чата работал, даже когда сама панель закрыта. Логика понятная, но у неё есть реальная цена: `socket.io-client` и вся логика чата грузятся и открывают real-time соединение на **каждой** странице для **каждого** залогиненного пользователя — включая тех, кто никогда не пользуется чатом поддержки.

Раз в коде нигде нет `next/dynamic`, весь этот код почти наверняка едет в общий (shared) JS-чанк, который download'ится на каждой странице ещё до первой отрисовки.

**Не обязательно менять поведение** (бейдж непрочитанного — это осознанный компромисс), но саму JS-загрузку компонента можно вынести в `next/dynamic({ ssr: false })` без потери функциональности — тогда она подгрузится асинхронно, не блокируя критический путь рендера остальной страницы.

## Важно

### 4. Мёртвый импорт тянет за собой карту `@2gis/mapgl` в форму подачи объявления

Файл: `client/src/components/features/ads/components/ad-form.tsx`, строка 43: `import { MapAd } from './map-ad'`.

Сам компонент `<MapAd .../>` закомментирован (строка ~325) — карта на форме сейчас нигде не используется, о чём прямо говорит комментарий в соседнем `use-geolocation.ts`. Но **импорт остался живым** — а раз `MapAd` формально ссылается на `@2gis/mapgl` (обычно довольно тяжёлая библиотека карт), есть риск, что она всё ещё попадает в бандл страницы подачи объявления, даже если сам компонент никогда не рендерится. Зависит от того, насколько агрессивно tree-shaking у сборщика вычищает импортированный-но-неиспользуемый named export — без реального билда я не могу сказать однозначно, попадает она в чанк или нет, но сам факт мёртвого импорта — как минимум, source of truth, который стоит либо убрать, либо (если карту всё же собираются вернуть) явно обернуть в `next/dynamic`.

### 5. Категорийные PNG-иконки тяжелее, чем должны быть для своего размера

`client/public/images/categories/*.png` — 14 файлов, самые крупные: `zemli-i-obuekty-sh-nedvizhimosti.png` (637 КБ), `polevye-kultury.png` (309 КБ), `svezhaya-selhozprodukciya.png` (282 КБ) и т.д., суммарно на все 14 — около 3.4 МБ.

При этом реальные пиксельные размеры файлов небольшие (проверил несколько): 773×725, 430×437, 444×426 — то есть это не гигантские фото, а именно иконки/иллюстрации с альфа-каналом (RGBA), которые почему-то очень плохо сжаты как PNG. Для сравнения — иллюстрация такого размера в оптимизированном виде обычно весит 20-80 КБ, а не 300-650.

Раз они отдаются через `next/image` (`category-item.tsx` использует `<Image>`, не голый `<img>`) — на лету это всё равно конвертируется в AVIF/WebP и кешируется (в `next.config.ts` уже правильно настроено: `formats: ['image/avif', 'image/webp']`, `minimumCacheTTL: 31536000`), так что для конечного пользователя после первого прогрева кеша разница не катастрофична. Но: (а) сам сервер оптимизации тратит больше CPU/памяти на первую генерацию каждого варианта из тяжёлого source-файла, (б) при деплое/клонировании репозитория эти 3.4 МБ просто лишний вес, (в) если когда-нибудь эти файлы отдадутся мимо `next/image` (например, напрямую через CDN) — разница будет прямая. Стоит прогнать через `pngquant`/`oxipng` или пересохранить в WebP как source.

### 6. Две библиотеки иконок одновременно

`lucide-react` используется 69 раз, `react-icons` — **один раз** (в `auth-socials.tsx`). Держать в зависимостях сразу две библиотеки иконок ради одной картинки — лишний вес в `node_modules`/lock-файле и потенциально в бандле (react-icons печально известна тем, что при неаккуратном импорте тянет много лишнего, хотя один конкретный импорт обычно tree-shake'ится нормально). Тот один иконка, скорее всего, есть и в lucide, либо её можно заменить на инлайн-SVG.

## По мелочи (стоит знать, не горит)

### 7. `shadcn` в `dependencies`, а не в `devDependencies`

`shadcn` — это CLI-генератор компонентов (используется командой `npx shadcn add ...`), не рантайм-библиотека. На бандл браузера не влияет (в клиентском коде он не импортируется), но по-хорошему должен жить в `devDependencies` — вопрос гигиены `package.json`, не скорости.

### 8. Пакет `add` в зависимостях

`"add": "^2.0.6"` в `dependencies` — похоже на случайность (типичный результат `npm install add` вместо использования `add` как отдельной команды где-то в терминале). Сам по себе крошечный, реальной пользы в рантайме, скорее всего, не несёт — стоит проверить, используется ли он вообще (`grep -r "from 'add'"`), и если нет — убрать.

### 9. Нет `"sideEffects": false` в `package.json`

В проекте 56 barrel-файлов `index.ts` с `export * from ...` (стандартный паттерн для фич-папок). Без объявления `"sideEffects": false` (или списка реально side-effectful файлов, например `globals.css`) сборщик по умолчанию консервативно считает, что у любого модуля могут быть побочные эффекты, и tree-shaking через такие barrel-файлы работает не так агрессивно, как мог бы. Это не сломает сборку, но потенциально оставляет в бандлах чуть больше кода, чем реально используется на конкретной странице.

### 10. Яндекс.Вебвизор включён

`YandexMetrika` (сам компонент реализован аккуратно — `next/script` со `strategy='afterInteractive'`, не блокирует рендер) инициализирует Метрику с `webvisor: true` — запись сессий пользователя. Это осознанная фича, не баг, но стоит иметь в виду: вебвизор — сам по себе не самая лёгкая штука в рантайме (мониторит все DOM-мутации/клики), это осознанный компромисс "аналитика vs немного CPU у каждого посетителя", а не техническая недоработка.

### 11. Хорошие новости — что уже сделано правильно

Чтобы не создавалось однобокой картины — часть базовых вещей уже сделана как надо, ломать не нужно:
- Нигде нет голых `<img>` — всё идёт через `next/image` (15 файлов), включая корректные `sizes`/`priority` (в разумных местах) и `width`/`height`.
- `next/font/google` для шрифта, с `display: 'swap'`, разумное число начертаний (4 веса × 2 подмножества).
- `next.config.ts`: `output: 'standalone'`, AVIF/WebP для картинок с годовым кешем, белый список хостов для `remotePatterns`.
- Сжатие (gzip) на API уже включено через `compression()` в `server/src/main.ts`, а фронтовый Next-сервер сжимает по умолчанию сам (`compress` не отключён) — на уровне nginx отдельно настраивать не обязательно, всё уже покрыто на уровне приложений.
- React Compiler включён в проде (`reactCompiler: process.env.NODE_ENV === 'production'`).
- Глобальный `staleTime: 60000` в React Query осознанно откалиброван, чтобы не дублировать запросы поверх SSR-данных.

## Отдельно, не совсем про скорость, но заметил по пути

В `tanstack-query-provider.tsx` стоит `retry: false` с комментарием `"на время отладки"` — то есть это временная настройка для дебага, которая, похоже, осталась в проде. Из-за неё любой прошедший мимо (например, разовый сетевой сбой) запрос не переповторяется вообще, хотя дефолтное поведение React Query (3 попытки с backoff) обычно и существует именно ради устойчивости к таким вещам. Не про скорость загрузки, но раз уж просматривал этот файл — показалось важным не упустить.

## Если хочешь двигаться дальше

Порядок, в котором я бы брался за находки (по соотношению эффект/усилия):
1. Пункт 1 (priority на 14 картинках) — самое дешёвое и прямое влияние на LCP.
2. Пункт 3 и часть пункта 2 (dynamic import для лайтбокса/чата/капчи/dadata) — не так дёшево, но самый большой суммарный эффект на общий вес JS.
3. Пункт 4 (мёртвый импорт карты) — тривиально удалить или обернуть.
4. Пункт 5 (сжать PNG) — разовая задача, не требует правок кода.
5. Остальное — по мере возможности, не горит.

Могу прогнать более точные цифры (реальный `npm run build` с таблицей размеров по роутам), если пришлёшь его вывод из своего терминала, либо если попробуем ещё раз через среду, где `node_modules` и сеть совпадают с целевой платформой.
